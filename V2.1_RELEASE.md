# V2.1 — Supervisor Command Center

## Architecture reviewed before implementation

The application is dependency-free vanilla JavaScript. `js/app.js` owns hash navigation and deferred rendering; `js/ui.js` provides DOM, dialog and feedback primitives. Views read the shared store through the derived model. The store handles local persistence, versioned per-record merges, deletion tombstones, cloud/shared-file transport and JSON backup.

Machine imports own production queues. Daily Schedule and the project colour reference remain isolated read-only sources. Manual tasks, status overrides, assignment, parking, routing, back orders and rush flags retain their existing ownership and behaviour.

The same source builds a modular hosted PWA and a self-contained `Cutting-Tracker.html`. No framework, runtime dependency, external font, CDN or database migration was introduced. Existing tests are unchanged; new Command Center checks are appended to the test command.

## What changed

- Overview becomes the Supervisor Command Center while retaining its hash, navigation label, operational priorities and completion/undo controls.
- A shared visual layer updates navigation, surfaces, spacing, typography, status treatments, desktop and mobile layouts in both themes. The existing print and monitor experiences remain separate.
- Machine cards prioritize reported downtime, old down flags requiring confirmation, shortages and tracked active work. Group and attention filters and an expandable list make all configured visible machines reachable. The unassigned CNC holding queue is not counted as a physical machine.
- Downtime and quality reports support owner, priority, machine, date, work order and optional measured minutes or affected quantity. Reports can be edited, resolved and reviewed after resolution.
- Reports use optional `operation` metadata on existing todos. They appear in Today and use its existing persistence, sync, export, deletion and completion behaviour. Legacy todos remain general actions. Unknown time remains unknown; resolving a report does not erase measured daily lost time.
- Handover coverage counts visible machines with substantive saved notes, completed work or next jobs. Blank rows and operator counts alone do not count. Links select the named shift, including the last ended shift overnight. Open issues can be reviewed and inserted into general notes without silently saving the handover or repeatedly inserting unchanged lines.
- Mobile navigation gains a labelled page search and an explicit empty state.

## Metric boundaries

Schedule completion is a percentage of imported/scoped lines, not pieces, shift target attainment or OEE. Active work is a tracked line state, not machine telemetry. Imported down reports retain their source date and require floor confirmation. Measured lost minutes total reports for the displayed calendar day, including resolved reports; reports without minutes are counted separately. Quality issues are open report counts, not defect or rejection rates. Scheduled quantities and job statuses are never changed by creating a quality report.

Operational reports are follow-ups, not a maintenance event timer or a formal non-conformance disposition system. Closing a downtime report does not clear a workbook down flag. Reports created on an older client remain ordinary todos; the metadata is carried by the existing per-record merge.

## Validation

The existing npm test chain is preserved. Added `test:command` verifies validation, loss totals, carryover, hidden machines, handover coverage, persistence, merges, and a mobile create/edit/reload/filter/resolve/handover/navigation workflow.

This environment returns `ERR_EMPTY_RESPONSE` for the intentionally unreachable `example.invalid` cloud probe. The unchanged baseline and V2.1 both complete the app assertions but fail that console-error check because it expects a different network error. Tests have not been weakened to conceal it. Importer/store rules, machine checks, cloud sync, photo workflow, routing, visual QA, size budgets, offline operation, standalone operation and both new Command Center checks pass. Both builds pass. Existing full-app assertions complete; its final console-error gate is the known baseline failure. The modular first load remains within the existing 1,100 KB and 40-request budgets (1,080 KB, 40 requests).
